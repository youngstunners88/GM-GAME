## Q1 — Committed DROP on lock-release

Root cause guess: hover anchor Y is likely anchored once (spawn Y), not re-anchored to the player — so it "chases" in X only and camps 250px up. Fix = re-anchor + a **committed, uncancellable DROP state** the lock logic cannot interrupt.

```gdscript
enum State { HOVER, DROP_WINDUP, DROP, RECOVER }
const HOVER_DY      := 72.0    # ride 72px above player, not 250
const DROP_SPEED    := 520.0   # px/s, ~3-4x hover drift -> reads as intent
const DROP_COMMIT_T := 0.55    # uninterruptible window
const WINDUP_T      := 0.22    # telegraph dip
const STRIKE_BAND   := 56.0    # |dy| to exit drop
const DROP_RANGE_X  := 420.0   # don't dive cross-map
const SPAWN_GRACE_T := 1.5     # no drop right after aggro -> no sweep-kill

func _on_lock_released():                       # your existing hysteresis exit
    if state == State.HOVER and _aggro_t > SPAWN_GRACE_T \
       and absf(player.x - x) < DROP_RANGE_X:
        state = State.DROP_WINDUP; _t = 0.0

func _physics_process(dt):
    _aggro_t += dt
    match state:
        State.HOVER:
            _hover_anchor_y = player.global_position.y - HOVER_DY  # re-anchor EVERY frame
            _drift_toward(player.x, _hover_anchor_y, dt)
        State.DROP_WINDUP:
            _t += dt; position.y += 40.0 * dt    # small dip = telegraph
            if _t >= WINDUP_T: state = State.DROP; _t = 0.0
        State.DROP:
            _t += dt
            velocity.x = signf(player.x - x) * 120.0   # slight track, mostly vertical
            velocity.y = DROP_SPEED
            move_and_slide()
            var dy = player.global_position.y - global_position.y
            if dy < STRIKE_BAND or _t >= DROP_COMMIT_T or is_on_floor():
                state = State.RECOVER; _t = 0.0
        State.RECOVER:                            # ease back to hover band
            _t += dt
            velocity.y = lerpf(velocity.y, -140.0, 8.0 * dt)
            move_and_slide()
            if _t >= 0.4: state = State.HOVER
```

Key rules: DROP ignores lock re-acquire (commit), contact damage off during WINDUP + first 0.15s of DROP, re-hover target is `player.y - 72` not a stored absolute Y.

## Q2 — E advances AND closes (same-press double-fire)

Cause: two handlers see the same press in one frame — the opener's press leaks into the just-opened dialogue, or advance+close both listen. Polling `Input.is_action_just_pressed()` in `_process` **cannot be consumed** — everyone polling that frame gets `true`. Fix: event-driven, single owner, handled-flag, release-gate.

```gdscript
# DialogueBox.gd — the ONLY node that reacts to "interact" while open
var _await_release := false

func open(lines: Array) -> void:
    _lines = lines; visible = true
    _await_release = true            # the press that opened us must be released first
    get_viewport().set_input_as_handled()   # eat the opening event

func _unhandled_input(event: InputEvent) -> void:
    if not visible: return
    if _await_release:
        if event.is_action_released(&"interact"):
            _await_release = false
        get_viewport().set_input_as_handled()
        return
    if event.is_action_pressed(&"interact"):
        if not _advance():           # returns false on last line
            close()
        get_viewport().set_input_as_handled()   # nothing else sees this press
```

Opener (NPC/player) also uses `_unhandled_input` + `event.is_action_pressed(&"interact")`, then calls `dialogue.open(...)` — the `set_input_as_handled()` inside `open()` stops the same event reaching anything else.

Checklist:
- Delete any `Input.is_action_just_pressed("interact")` polling in `_process`/`_physics_process` — this is the bug 9/10 times.
- Project → Input Map: confirm `E` is **not** also bound to `ui_accept` (default ui_accept = Enter/Space, but check). If the box is a Control with focus, `ui_accept` fires `_gui_input` separately → set `focus_mode = FOCUS_NONE` on it.
- One owner per action per game state: while dialogue visible, player script must early-return on `dialogue.visible` (or pause the player tree branch).
