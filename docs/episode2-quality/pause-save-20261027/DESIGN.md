# Pause and manual checkpoint saves — 2026-10-27

Owner request: visible Pause and Save buttons in Episodes1 and2, with progress recoverable at different points.

Both episodes have two visible top-right buttons: pause/play and a disk. Escape/gamepad pause opens the pause card; Escape resumes it. Episode1's pause menu also has Save checkpoint and displays its restore point. Episode2 retains its play/home card and gains the shared save control. Controls use real Buttons plus deduplicated raw touch taps, so a second finger can save while a steering thumb remains down. Touch has drawn icons; desktop gets tooltips and success/failure text. Other modals, transitions and the existing film/portrait ownership remain protected.

The save is the latest explicit checkpoint, not an exact-frame world snapshot or multiple slots. Episode1 uses the current stage's last activated checkpoint, or stage start. Episode2 uses the current runner/chamber section start. Save shows the named restore point. Progress since that point is replayed on Continue. Entry-time inventory, purse, economy and reward guards are frozen together, so replaying a partially completed section does not retain its later spending/rewards alongside a reset scene. Episode2's supplied cast, films, progression and dialogue order remain intact.

Manual checkpoint data lives inside the existing session format and is independent of subsequent rolling autosaves. Snapshot data never includes the manual slot recursively. A temporary file is flushed and renamed; failed writes report failure and preserve the old save. On web, the explicit checkpoint uses a small synchronous, atomic localStorage record and success is shown only after setItem returns successfully. The existing IndexedDB filesystem remains the rolling/compatibility save; its asynchronous flush cannot overwrite the explicit record. Blocked/full storage reports failure and preserves the prior record. No save data or user input is interpolated into executable JavaScript; JSON goes through the bridge as a string. Browser reload tests must exercise both episodes and the actual Continue route. A new session can overwrite rolling data while the explicit checkpoint remains until the player saves another checkpoint. Existing saves without a manual record still load. Untrusted records are bounded, validated and clamped by the existing save readers; they never grant an Episode2 access unlock.

The existing main-menu Continue handler is preserved with all five founder-locked title files unchanged. It already calls load_session then level_scene; that route now consumes a pending manual checkpoint only while on the real menu. Continue selects its saved Episode1 level or Episode2 entry; Episode2 consumes its checkpoint after the unchanged access gate. Explicit replay still starts a new run. Saves are local to the same browser/device; there is no new cloud/wallet save service.

Implementation: GameManager snapshot/write/restore, LevelBase and checkpoint capture, Ep2SessionRoot section metadata/reward restoration, Ep2Entry pause/Continue integration, shared RunControls, PauseMenu and the existing touch card. No Meshy or other paid services are needed.

Verification: manual_checkpoint_test30 checks; existing save compatibility, Episode2 touch and touch-profile suites; pause tests retain only the three previously documented local HUD-geometry differences.
